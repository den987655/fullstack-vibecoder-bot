# ADR-0002: Переход от HTTP Polling к Supabase Realtime для сообщений диалога## Метаданные- **Статус:** Accepted- **Дата:** 2026-10-13- **Авторы:** Команда разработки fullstack-vibecoder-bot- **Связанные документы / файлы:**  - ADR по Supabase: [docs/adr/0001-use-supabase-and-studio-ui.md](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/docs/adr/0001-use-supabase-and-studio-ui.md)  - Use Case бота: [temp.ts](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/temp.ts)  - Миграция Realtime: [02-lesson/supabase/migrations/20261013115133_enable_realtime_messages.sql](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/02-lesson/supabase/migrations/20261013115133_enable_realtime_messages.sql)  - React Query хуки: [02-lesson/frontend/src/pages/messenger/api/messageQueries.ts](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/02-lesson/frontend/src/pages/messenger/api/messageQueries.ts)  - Инструкция проекта: [agent.md](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/agent.md)---## 1. Контекст и проблематика (Context & Problem Statement)В проекте **fullstack-vibecoder-bot** ключевым сценарием является живое общение между пользователем в Telegram и оператором в веб-интерфейсе:1. Пользователь пишет боту в Telegram или нажимает инлайн-кнопки (например, запрос конвертации валюты `100 EUR` или инверсия курса `rev|EUR|100|...`).2. В файле [temp.ts](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/temp.ts) класс `HandleMessageUseCase` мгновенно записывает как входящее сообщение пользователя, так и исходящий ответ бота в PostgreSQL через `supabaseRepository.saveClientAndMessage(...)`.3. Оператор в веб-интерфейсе (`02-lesson/frontend`) должен видеть переписку в режиме реального времени, чтобы вовремя подключиться к диалогу или проконсультировать клиента.### Исходная реализация (HTTP Polling):На первом этапе в [messageQueries.ts](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/02-lesson/frontend/src/pages/messenger/api/messageQueries.ts) обновление сообщений было реализовано через периодический опрос (polling) средствами TanStack Query:```typescriptexport const useMessages = (dialogId: number | null) => {  return useQuery({    queryKey: ['messages', dialogId],    queryFn: () => fetchApi<Message[]>(`/messages?clientId=${dialogId}`),    enabled: !!dialogId,    refetchInterval: 2000, // опрос каждые 2 секунды  });};```### Проблемы подхода с HTTP Polling:1. **Задержка пользовательского опыта (Latency до 2 сек):** Когда клиент отправляет сообщение в Telegram, оператор видит его не сразу, а с задержкой от 0 до 2000 мс. В сценарии живого саппорт-чата это создает ощущение «тормозящего» интерфейса.2. **Паразитный сетевой трафик и вызовы Edge Functions:** Каждые 2 секунды браузер шлет HTTP GET-запрос к функции `/messages`. При 99% таких запросов новых сообщений нет. В бессерверной среде (Edge Functions) каждый запрос расходует квоту вызовов, процессорное время и нагружает соединение с базой данных.3. **Проблема масштабирования:** Если у оператора открыто несколько вкладок или в системе одновременно работают десятки операторов, частота пустых запросов кратно возрастает, создавая риск превышения лимитов и исчерпания пула соединений PostgreSQL.---## 2. Рассмотренные альтернативы (Considered Options)### Вариант 1: Сокращение интервала Polling (например, до 500 мс)- **Плюсы:** Не требует изменений в архитектуре сетевого взаимодействия.- **Минусы:** В 4 раза увеличивает количество бесполезных запросов (120 req/мин на одного оператора), усугубляя проблему нагрузки на сервер и сеть, но не давая по-настоящему мгновенного отклика.### Вариант 2: Собственный WebSocket-сервер (Node.js / ws / Socket.io + Redis Pub/Sub)- **Плюсы:** Полный контроль над протоколом сокетов.- **Минусы:**   - Требует отдельного постоянно работающего инстанса (VPS/контейнера), что противоречит бессерверной модели Deno Edge Functions.  - Необходимость написания кода синхронизации между Telegram-ботом и сокет-сервером (через Redis pub/sub или Postgres LISTEN/NOTIFY).  - Высокие расходы на инфраструктуру и поддержку.### Вариант 3: Supabase Realtime (WebSockets на базе PostgreSQL Logical Replication) — ВЫБРАНО- **Плюсы:**  - **Нулевой оверхед по бэкенд-коду:** Не нужно писать свой сокет-сервер. Supabase Realtime напрямую слушает журнал упреждающей записи PostgreSQL (Write-Ahead Log, WAL) через логическую репликацию (`publication supabase_realtime`).  - Как только [temp.ts](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/temp.ts) выполняет `INSERT` в `public.messages`, событие мгновенно (50–100 мс) публикуется всем подключенным клиентам по WebSockets.  - Гибкая фильтрация: возможность подписаться только на сообщения конкретного диалога (`filter: 'client_id=eq.' + dialogId`).  - Интеграция с Row Level Security (RLS) PostgreSQL.- **Минусы:**  - Требуется включение таблицы в публикацию и настройка политик RLS на чтение для Realtime.  - На фронтенде необходимо корректно управлять жизненным циклом сокет-подписки (подписка при выборе диалога, отписка при смене диалога или анмаунте).---## 3. Принятое решение (Decision Outcome)Перейти от периодического HTTP-опроса (`refetchInterval`) к **Supabase Realtime (WebSockets)** для доставки сообщений диалога оператору.### Техническая реализация решения:#### 1. Уровень базы данных (PostgreSQL)Создана и применена миграция [20261013115133_enable_realtime_messages.sql](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/02-lesson/supabase/migrations/20261013115133_enable_realtime_messages.sql):```sql-- 1. Добавление таблицы messages в публикацию realtimeALTER PUBLICATION supabase_realtime ADD TABLE public.messages;-- 2. Установка REPLICA IDENTITY FULL для передачи полной строки при событияхALTER TABLE public.messages REPLICA IDENTITY FULL;-- 3. Политика RLS для разрешения чтения realtime-событийDROP POLICY IF EXISTS "Allow read messages for realtime" ON public.messages;CREATE POLICY "Allow read messages for realtime" ON public.messages FOR SELECT TO anon, authenticated USING (true);```#### 2. Архитектура потока данных (Data Flow)```Telegram User      │     ▼ (Webhook)Deno Edge Function (clean-architecture-bot)     │     ▼ (temp.ts: HandleMessageUseCase.execute / handleCallback)supabaseRepository.saveClientAndMessage(...)     │     ▼ (INSERT into public.messages)PostgreSQL WAL (Write-Ahead Log)     │     ▼ (Logical Replication)Supabase Realtime Engine (Elixir / Phoenix WebSockets)     │     ▼ (WebSocket Channel: postgres_changes)React Frontend Operator Panel (ChatArea.tsx / TanStack Query Cache)     │     ▼ (<50ms)Мгновенное отображение нового сообщения на экране оператора```#### 3. Уровень фронтенда1. **Первоначальная загрузка (Initial Fetch):** При открытии диалога оператором выполняется стандартный HTTP-запрос через `fetchApi` для получения истории сообщений.2. **Realtime-подписка:** Подключение канала сокетов к таблице `public.messages`. При наступлении события `INSERT` новое сообщение добавляется напрямую в кэш TanStack Query (`queryClient.setQueryData`) или триггерит инвалидацию кэша без задержки.3. **Отключение Polling:** Параметр `refetchInterval` убирается (или переводится в режим fallback на случай потери WebSocket соединения).---## 4. Последствия и компромиссы (Consequences)### Положительные:- **Мгновенная доставка:** Сообщения от Telegram-клиента и ответы бота отображаются в чате оператора за миллисекунды (<100 мс) вместо 2 секунд.- **Снижение серверной нагрузки на 95%:** Прекращаются тысячи бесполезных HTTP-запросов к Edge Functions при открытой панели оператора.- **Сохранение чистой архитектуры бота:** [HandleMessageUseCase](file:///E:/react/fullstack-vibecoder/fullstack-vibecoder-bot/temp.ts) не знает о существовании операторского интерфейса и WebSockets; он просто пишет данные в репозиторий, а репликация происходит автоматически на уровне СУБД.### Отрицательные и компромиссы:- Необходимость управления состоянием соединения (обработка дисконнектов, reconnect, индикация статуса онлайн/офлайн сокета в UI).- Необходимость аккуратной отписки от каналов при смене активного диалога, чтобы избежать утечек памяти и задвоения сообщений.---## 5.
