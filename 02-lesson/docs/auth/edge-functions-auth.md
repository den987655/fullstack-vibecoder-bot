# Защита Supabase Edge Functions авторизациейДокументация по реализации защиты серверных функций (Supabase Edge Functions на Deno) с проверкой JWT токена пользователя и автоматической передачей токена с фронтенда.---## 1. Обзор архитектуры```[ Frontend (React / Vite) ]        |        | 1. fetchApi('/articles')        |    Headers:        |    - apikey: <VITE_SUPABASE_ANON_KEY>        |    - Authorization: Bearer <user_access_token>        v[ Supabase Edge Functions (Deno) ]        |        | 2. requireAuth(req)        |    - Проверка наличия 'Authorization: Bearer ...'        |    - Отклонение анонимного ключа (USER_TOKEN_REQUIRED)        |    - auth.getUser(token) -> валидация JWT        |        +-----> Невалиден / Истек ----> HTTP 401 Unauthorized        |        +-----> Валиден: UserContext { user, supabaseClient }                    |                    v          [ PostgreSQL + RLS ]          Выполнение SQL-запроса от имени пользователя```---## 2. Защищенные Edge Functions в проектеВсе эндпоинты модуля `02-lesson/supabase/functions` защищены централизованным валидатором:| Edge Function | Путь | Методы | Требование авторизации || :--- | :--- | :--- | :--- || **`articles`** | `/functions/v1/articles` | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` | **User JWT** (Авторизованный пользователь) || **`messages`** | `/functions/v1/messages` | `GET` | **User JWT** (Авторизованный пользователь) || **`client`** | `/functions/v1/client` | `GET` | **User JWT** (Авторизованный пользователь) |---## 3. Серверный модуль проверки авторизации (`_shared/auth.ts`)Функция `requireAuth(req: Request)` выполняет 3 этапа проверки:1. **Проверка заголовка**: проверяет наличие `Authorization: Bearer <token>`. Если отсутствует, возвращает `401 Unauthorized` с кодом `UNAUTHORIZED`.2. **Блокировка анонимного ключа**: проверяет, что передан персональный токен пользователя, а не базовый `SUPABASE_ANON_KEY`. Если передан анонимный ключ, возвращает `401` с кодом `USER_TOKEN_REQUIRED`.3. **Верификация JWT**: обращается к `auth.getUser(token)`. Если токен поддельный или истек, возвращает `401` с кодом `INVALID_TOKEN`.4. **Контекст пользователя**: при успешной проверке создает клиент Supabase с заголовком пользователя `Authorization: authHeader`, что гарантирует автоматическое применение политик **Row Level Security (RLS)** в базе данных PostgreSQL.---## 4. Клиентская часть: передача токена (`frontend/src/shared/api/base.ts`)Функция-обертка `fetchApi` автоматически внедряет токен текущей сессии:```typescript// Извлечение текущего access_token из стора сессии Supabaseconst { data: { session } } = await supabase.auth.getSession();if (session?.access_token) {  headers['Authorization'] = `Bearer ${session.access_token}`;}```### Преимущества:- Все запросы через React Query (`useMessages`, `useClients`, `useArticles`) автоматически авторизованы, как только пользователь входит в аккаунт через форму `LoginModal`.- Если пользователь выходит из системы (`logout`), заголовок автоматически возвращается к базовому состоянию, а попытки запроса защищенных функций корректно получают `401`.---## 5. Форматы ответов при ошибках авторизации```json// Отсутствует заголовок{  "error": "Требуется авторизация: заголовок Authorization с токеном Bearer отсутствует",  "code": "UNAUTHORIZED"}// Передан анонимный ключ вместо токена пользователя{  "error": "Доступ запрещен: требуется токен авторизованного пользователя (User JWT), а не анонимный ключ",  "code": "USER_TOKEN_REQUIRED"}// Истекший или невалидный токен{  "error": "Доступ запрещен: jwt expired",  "code": "INVALID_TOKEN"}```
