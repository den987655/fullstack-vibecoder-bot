# Classic Refresh & Access Token AuthorizationДокументация и детальная диаграмма последовательности (Sequence Diagram) для классической схемы двухтокеновой авторизации (**Access Token** + **Refresh Token**).---## 1. Обзор архитектурыКлассическая схема использует разделение полномочий на два типа токенов:| Параметр | Access Token | Refresh Token || :--- | :--- | :--- || **Назначение** | Аутентификация и авторизация запросов к защищенным API | Получение новой пары токенов после истечения Access Token || **Формат** | Обычно JWT (содержит claims: `userId`, `roles`, `exp`) | Opaque токен (случайная строка высокой энтропии) или JWT || **Срок жизни** | Короткий (5 — 15 минут) | Длинный (7 — 30 дней) || **Место хранения (Клиент)** | Память приложения (in-memory state / closures) | Защищенный `HttpOnly, Secure, SameSite` Cookie || **Хранение на сервере** | Не хранится в БД (stateless валидация по подписи) | Хранится в БД/Redis (хэш токена, статус сессии, устройство) || **Возможность отзыва** | Только по истечении срока жизни (или через blacklist) | Мгновенно (удаление сессии / инвалидация в БД) |---## 2. Детальное описание этапов### 1. Первичная авторизация (`/api/auth/login`)1. Клиент передает учетные данные пользователя (`email`/`password`) по защищенному каналу HTTPS.2. Бэкенд валидирует пароль (хэш с солью через Argon2id / bcrypt).3. Создается:   - **Access Token**: JWT со сроком жизни ~15 минут.   - **Refresh Token**: криптографически стойкая случайная последовательность (32+ байта в base64url) со сроком жизни ~30 дней.4. В хранилище сессий (PostgreSQL или Redis) сохраняется запись:   ```json   {     "session_id": "uuid-v4",     "user_id": "user-uuid",     "refresh_token_hash": "sha256_hash_of_token",     "user_agent": "Mozilla/5.0 ...",     "ip_address": "192.168.1.1",     "expires_at": "2026-11-26T12:00:00Z",     "created_at": "2026-10-27T12:00:00Z"   }   ```5. Клиент получает:   - В теле ответа (JSON): `accessToken` и публичные данные пользователя.   - В заголовке `Set-Cookie`: `refreshToken` с флагами `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`.---### 2. Обычный защищенный запрос1. Клиент добавляет заголовок `Authorization: Bearer <accessToken>`.2. API Gateway / Бэкенд верифицирует подпись токена с помощью публичного ключа (RS256/EdDSA) или общего секрета (HS256).3. Проверяется срок годности токена (`exp`).4. Если подпись и срок валидны, запрос выполняется **без обращения к БД** (stateless), что гарантирует высокую производительность и масштабируемость.---### 3. Автоматическое обновление токена (Silent Refresh & Queue)Когда Access Token истекает:1. Защищенный API возвращает `401 Unauthorized` с телом ошибки (например, `{ code: "TOKEN_EXPIRED" }`).2. **HTTP Interceptor на клиенте** перехватывает этот статус:   - Если уже идет процесс обновления (`isRefreshing === true`), текущий запрос складывается в очередь промисов.   - Если процесс еще не запущен, устанавливается флаг `isRefreshing = true` и выполняется `POST /api/auth/refresh`.3. Браузер автоматически прикрепляет HttpOnly cookie с `refreshToken`.4. Бэкенд хэширует полученный Refresh Token и сверяет с записью в БД.5. **Token Rotation (Ротация токенов)**:   - Старый Refresh Token инвалидируется.   - Генерируется **новая пара**: свежий Access Token и свежий Refresh Token.   - Запись сессии в БД обновляется новым хэшем.6. Клиент обновляет Access Token в оперативной памяти и повторяет все зависшие в очереди запросы с новым токеном.---### 4. Обнаружение повторного использования (Token Reuse Detection)Если злоумышленник перехватил старый Refresh Token и пытается применить его после того, как легитимный клиент уже совершил ротацию:1. Бэкенд видит попытку использовать уже неактуальный (ротированный) токен.2. Это признак кражи токена (Token Compromise).3. Бэкенд **немедленно инвалидирует всю цепочку сессий** данного пользователя (`is_revoked = true` для всей семьи токенов).4. Оба (злоумышленник и настоящий пользователь) выбрасываются из системы, защищая учетную запись.---### 5. Выход из системы (`/api/auth/logout`)1. Клиент отправляет запрос `POST /api/auth/logout`.2. Бэкенд удаляет или помечает отозванной сессию в БД.3. Бэкенд выставляет заголовок `Set-Cookie: refreshToken=; Max-Age=0` для очистки cookie в браузере.4. Клиент обнуляет `accessToken` в памяти.---## 4. Рекомендации по безопасности| Угроза | Мера защиты || :--- | :--- || **XSS (Cross-Site Scripting)** | `Refresh Token` хранится строго в `HttpOnly` Cookie. JavaScript в браузере не имеет к нему доступа, что делает невозможным его кражу через XSS. `Access Token` хранится только в памяти приложения (не в `localStorage`). || **CSRF (Cross-Site Request Forgery)** | Cookie с токеном снабжаются атрибутом `SameSite=Strict` (или `Lax`) + `Secure`. Для критичных операций используется дополнительный заголовок/CSRF-токен или ограничение `Path=/api/auth`. || **Кража Access Token** | Максимально сокращается срок жизни Access Token (5–15 минут). Ущерб от перехвата минимизирован временем его действия. || **Кража Refresh Token** | Применяется **Refresh Token Rotation (RTR)** с детектированием повторного использования и привязкой сессии к Fingerprint (User-Agent, IP subnet). |---## 5.
